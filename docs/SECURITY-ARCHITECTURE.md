# Security architecture

This document records how the public website is secured, what the hosting platform can and cannot
enforce, and what would change on a different host. It describes this **website** only; nothing
about the private APOLLO Network system belongs in this repository.

## Threat model in one paragraph

The site is static HTML, CSS, fonts, images and a few small scripts. It has no server code, no
database, no sessions, no accounts, no forms that submit anywhere and no user-generated content.
The realistic risks are therefore: a malicious or compromised dependency or build action; a
secret committed by mistake; DOM-based script injection introduced by future code; and content
that over-shares private details about the APOLLO system. The controls below are aimed at those.

## Controls implemented

| Area                    | Control                                                                                                                                                                                                                                                                                                                                                                                                                                            | Where                                                            |
| ----------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------- |
| Content Security Policy | `<meta http-equiv="Content-Security-Policy">` on every page, generated by Astro with SHA-256 hashes for every inline script and style. `default-src 'none'`; scripts, styles, fonts, images and the manifest limited to `'self'` + hashes; `connect-src`, `frame-src`, `object-src`, `worker-src`, `media-src` all `'none'`; `base-uri 'none'`; `form-action 'none'`; `upgrade-insecure-requests`. ## What GitHub Pages cannot do

GitHub Pages does not let a site set its own HTTP response headers. Consequences:

| Desired control                  | Status on GitHub Pages                                                    | Mitigation here                                                                                                                                                                                                                                                                                 |
| -------------------------------- | ------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `Content-Security-Policy` header | Not configurable                                                          | Delivered as a `<meta>` element instead. Equivalent for everything the site uses, with the gaps below. The meta element is emitted by Astro after the page's own `<head>` elements (static font styles, JSON-LD); those precede the policy but are build-time content, not attacker-influenced. |
| `frame-ancestors` (clickjacking) | Ignored by browsers in a `<meta>` CSP; `X-Frame-Options` not configurable | **Not enforced.** Other sites can frame these pages. Impact is low because the site has no authenticated state or state-changing actions to trick a visitor into. JavaScript frame-busting is not used: it is unreliable and can be defeated by sandboxed frames.                               |
| `report-uri` / `report-to`       | Not usable from `<meta>`                                                  | No violation reporting. Tested locally with a headless browser instead.                                                                                                                                                                                                                         |
| `Permissions-Policy`             | Not configurable, no `<meta>` equivalent                                  | **Not enforced.** The site's own code requests no powerful features (camera, microphone, geolocation, etc.) and loads no third-party code that could.                                                                                                                                           |
| `Referrer-Policy`                | Not configurable                                                          | `<meta name="referrer" content="no-referrer">`.                                                                                                                                                                                                                                                 |
| `X-Content-Type-Options`         | Not configurable                                                          | Not set by this project. Verify GitHub's current behaviour after deployment with `curl -sI`. Risk is low: every file is served with an extension-derived type and no user uploads exist.                                                                                                        |
| `Strict-Transport-Security`      | Not configurable                                                          | `*.github.io` is on browsers' HSTS preload list, so HTTPS is enforced for the default domain. Enable **Enforce HTTPS** in the Pages settings. For a future custom domain, HSTS would depend on the new host or DNS/CDN layer.                                                                   |
| `robots.txt` location            | A project site cannot serve the domain-root `/robots.txt`                 | `robots.txt` is generated under the base path and becomes authoritative on a custom domain. Until then, submit `sitemap.xml` directly to search consoles. See _Lighthouse SEO score_ below.                                                                                                     |

## Lighthouse SEO score (92) — cause and decision

Lighthouse reports **“robots.txt is not valid”** and scores SEO 92. This was investigated
precisely:

- Lighthouse fetches `/robots.txt` _from inside the page_, so the request is subject to the page's
  Content Security Policy. `connect-src 'none'` blocks it, and Lighthouse records the blocked
  fetch as an invalid robots.txt (“Protocol error … CSP violation”).
- Verified experimentally: a throwaway build with `connect-src 'self'` scores **SEO 100** (the audit
  becomes not-applicable because the domain root has no robots.txt).
- Search-engine crawlers fetch `robots.txt` directly, outside any page, so they are unaffected.

**Decision:** keep `connect-src 'none'`. The site makes no network requests from script, and
loosening a security directive only to change a lab score would be gaming the metric. If a future
feature legitimately needs same-origin `fetch`, `connect-src 'self'` becomes appropriate and the
score will change as a side effect.

## `upgrade-insecure-requests` and local previews

WebKit (Safari) applies `upgrade-insecure-requests` to plain-`http` loopback servers, while
Chromium and Firefox exempt them. A local `http://` preview in Safari may therefore load without
styles or scripts. Production is HTTPS-only, where the directive is a no-op safeguard. QA runs
WebKit against an HTTPS server so the production policy is tested unmodified.

## Migration path for full header control

If the site needs enforced headers (for example `frame-ancestors 'none'` and a `Permissions-Policy`),
move hosting to a static platform or CDN that supports custom headers, such as Cloudflare Pages,
Netlify, or GitHub Pages behind a CDN that rewrites headers. The migration is small because the
build is already host-agnostic:

1. Set `SITE_ORIGIN` and `SITE_BASE` (empty for a root domain) for the build.
2. Serve `dist/` unchanged.
3. Add response headers at the edge, e.g.:

   ```
   Content-Security-Policy: <copy the policy from any built page>; frame-ancestors 'none'
   Permissions-Policy: camera=(), microphone=(), geolocation=(), payment=(), usb=()
   Referrer-Policy: no-referrer
   X-Content-Type-Options: nosniff
   Strict-Transport-Security: max-age=63072000; includeSubDomains; preload
   Cross-Origin-Opener-Policy: same-origin
   ```

   Because Astro hashes inline content per build, generate the header from the built HTML during
   deployment rather than hard-coding it.

## If a secret is ever committed

Deleting the file is not enough: it remains in Git history and in any clone or fork.

1. **Revoke or rotate the credential immediately** at its issuer. Treat it as compromised.
2. Check the issuer's logs for use of the credential.
3. Remove it from history (for example with `git filter-repo`), force-push, and ask GitHub
   Support to purge cached views if needed. Anyone who cloned the repository still has it, which
   is why step 1 comes first.
4. Add a pattern to `tests/leak-scan.test.mjs` if the scanner missed it.
